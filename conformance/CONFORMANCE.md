## Verification Methodology

### Check 1: Audit Hash Self-Consistency
Five-step JCS (RFC 8785) + SHA-256 verification per RFC 001 §13.3:
1. Deep clone decision_object
2. Delete audit.hash / signature / signing_key_id
3. JCS serialize remaining fields
4. SHA-256 hash
5. Compare with stored audit.hash

### Check 2: Answers File Cross-Comparison
Independent oracle verification: recomputed canonical bytes are compared
against the pre-generated answers file. This catches runners that pass
Check 1 but produce incorrect canonical bytes, and vice versa.

A runner must pass **both** checks to be considered verified.

### AV-013: Chain Position Tampering Canary
AV-013 stores a regressed runner's audit.hash (audit object deleted from
JCS preimage). A correct runner (includes previous_hash) will produce a
different hash → MISMATCH in Check 1. The canonical bytes still match
the answers file in Check 2, confirming the canary correctly discriminates.
A regressed runner (excludes previous_hash) would produce a matching hash
→ the canary catches the regression.
